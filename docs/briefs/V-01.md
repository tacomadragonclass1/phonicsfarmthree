## API
```ts
export interface FencePoint { x: number; z: number }
export interface FenceOptions {
  picketSpacing?: number;   // 0.28
  picketWidth?: number;     // 0.16
  picketDepth?: number;     // 0.05
  picketHeight?: number;    // 0.95
  postEvery?: number;       // 2.0  (metres between thicker posts)
  railHeights?: [number, number];  // [0.32, 0.68]
}
/** One merged mesh for a run of fence along `path`, following the ground. */
export function buildFenceMesh(path: readonly FencePoint[], groundY: (x: number, z: number) => number, options?: FenceOptions): THREE.Mesh
/** Box colliders for the same run, one per ~2 m piece. */
export function fenceColliders(idPrefix: string, path: readonly FencePoint[], groundY: (x: number, z: number) => number, layer: number): StaticOptions[]
/** The shared fence texture/material source (a MeshStandardMaterial WITH a map, so the painted look can be applied). */
export function createFenceMaterial(): THREE.MeshStandardMaterial
```
### `buildFenceMesh`
- Walk the polyline. Every `picketSpacing` metres along it place one picket:
  a box `picketWidth` x `picketHeight` x `picketDepth`, its bottom at
  `groundY(x, z) - 0.05`, rotated about Y so its wide face is across the
  direction of travel (yaw of the segment = `Math.atan2(dx, dz)`; the box's
  local X must lie ALONG the segment, so rotate by `yaw + PI / 2`... verify
  with the test below rather than trusting this sentence).
  On top of each picket add a small pointed cap: a 4-sided
  `ConeGeometry(picketWidth * 0.62, 0.14, 4)` rotated 45 degrees about Y
  before the picket's own rotation.
- Every `postEvery` metres, and at every path vertex, place a post instead:
  0.2 x (picketHeight + 0.1) x 0.2 with a flat top.
- Rails: between each pair of consecutive pickets/posts, two thin boxes
  (0.07 tall, 0.04 deep) stretched from one to the next at the two
  `railHeights` above each end's own ground height, so they slope with the
  hill. Simplest correct construction: a unit box scaled to the distance,
  `lookAt`-style orientation from end A to end B.
- Use `BoxGeometry` clones transformed with `applyMatrix4`, then
  `mergeGeometries` from `three/examples/jsm/utils/BufferGeometryUtils.js`
  (make every piece non-indexed first with `toNonIndexed()` so box and cone
  merge). The result is ONE `THREE.Mesh` named `Fence`, in WORLD coordinates
  (mesh position 0,0,0), using `createFenceMaterial()`.
- UVs: leave whatever the primitives have.
### `createFenceMaterial`
A 4x4 `DataTexture` (RGBA, `SRGBColorSpace`, `NearestFilter` off -- use
`LinearFilter`) of warm whites that differ slightly per texel (around
rgb 244, 236, 220, varying by up to 10), `needsUpdate = true`;
`new MeshStandardMaterial({ map, roughness: 1 })`.
### `fenceColliders`
Split each path segment into pieces no longer than 2 m. Each piece: a box
with half extents `[length / 2, 0.6, 0.12]`, centre at the piece's middle,
`y = groundY(mid) + 0.6`, `yaw` such that the box's local X runs along the
segment (in this codebase a yaw rotates +Z toward +X, so a segment along +X
needs yaw 0 for a box that is long in X... verify with the test). Ids
`${idPrefix}-${n}`. `blocksCamera: false`.

## Tests
1. a straight 4 m path along +X on flat ground: the mesh's bounding box
   spans x from about -0.1 to 4.1, y from -0.05 to about 1.1, and is THIN in
   z (max |z| < 0.15).
2. the same path along +Z is thin in x. (This is what catches a wrong yaw.)
3. sloping ground (`groundY = x * 0.5`): the bounding box top is above 2.5
   at the far end -- pickets follow the ground.
4. `fenceColliders` for a 5 m path along +X gives 3 pieces whose half
   extents x sum to 2.5, ids `f-0..f-2`; a real `PhysicsWorld` with them
   added blocks `canReach` across the fence at x = 2.5 (from z = -1 to z = 1,
   y = 0.5) and does not block along it at z = 1.
5. the same along +Z blocks a ray crossing in x.
6. the material has a map.
